# 功能规格:Claude Code 流量离线滥用分析

**Feature Branch**: `004-traffic-abuse-analysis`

**Created**: 2026-07-11

**Status**: Draft

**Input**: 面向经网关(ModelGate 旁路)的 Claude Code 流量,离线批量分析每次请求"在干什么、是否与工作相关",并聚合到人做滥用识别。请求时先记录日志并提取压缩信号入库,`check --analyze` 命令异步分析、把结论写回请求日志、删除已分析的中间数据。

## 概述

网关每天转发大量 Claude Code 请求。管理员目前能看到用量(token、成本、次数),但看不懂**用户到底在用它做什么**,也无法判断是否存在**与工作无关的滥用**(个人副业、学习刷教程、娱乐等)。

本功能在**不影响转发链路、不增加任何请求延迟**的前提下,离线地为每条请求打上"在干什么"的标签(工具、任务类型、代码方向/文档动作、是否工作相关),并按人聚合出滥用评分,超阈值的人进入人工复核队列。为控制分析成本,系统先用**本地规则**尽可能定字段,只有规则拿不准时才调用外部 Haiku 模型补齐。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理员识别疑似滥用的人 (Priority: P1)

管理员定期(或按需)查看一份按人聚合的画像报表,能看到每个人在统计窗口内做了多少件事、其中多少与工作无关、滥用评分多高;评分超过阈值的人被自动放入复核队列,并附上"非工作原因"抽样,供管理员快速判断是否需要约谈或进一步处理。系统只做识别与提示,不做任何自动处罚。

**Why this priority**: 这是整个功能的最终业务价值——把海量请求变成"到人"的可行动结论。没有它,前面的分类和打标都只是中间产物。

**Independent Test**: 灌入一批已知的请求样本(含明显工作相关与明显非工作相关的),运行分析,确认报表中每个人的逻辑任务数、工作占比、滥用评分正确,且高分用户出现在复核队列并带有原因抽样。

**Acceptance Scenarios**:

1. **Given** 某人本窗口内的逻辑任务大多与工作无关,**When** 运行分析与聚合,**Then** 该人的滥用评分高于阈值并进入复核队列,报表展示其非工作原因抽样。
2. **Given** 某人本窗口内全部任务命中内部仓库且为工作相关,**When** 运行分析与聚合,**Then** 该人滥用评分低、不进入复核队列。
3. **Given** 复核队列中的某人被管理员查看,**When** 打开其条目,**Then** 能看到逻辑任务数、物理请求数、任务类型分布、代码方向分布、工作占比与原因抽样。

---

### User Story 2 - 逐条请求被打上"在干什么"的标签 (Priority: P1)

对每条经网关的 Claude Code 请求,系统识别出用到的工具、任务类型(代码/文档/其他)、以及代码方向或文档动作,并判断是否与工作相关及原因。分析结论回写到该请求对应的用量日志记录上,使管理员在明细层面也能看懂每条请求。

**Why this priority**: 聚合报表(Story 1)完全依赖逐条标签的质量;逐条标签本身也是明细排查(某条可疑请求到底在干嘛)的基础。

**Independent Test**: 取单条含明确文件后缀与内部仓库路径的请求,运行分析,确认其用量日志记录上出现正确的任务类型、代码方向、工作相关标记与原因。

**Acceptance Scenarios**:

1. **Given** 一条编辑 `.go` 文件、命中内部仓库路径的请求,**When** 分析完成,**Then** 其用量日志被标记为 代码 / 后端 / 工作相关,原因为"命中内部仓库 X"。
2. **Given** 一条只有工具结果回灌、没有新用户指令的请求(agent 循环轮),或一条由子代理(subagent)发起的请求,**When** 分析完成,**Then** 该请求被归为"工具续跑",不计为一件独立的逻辑任务,也不单独消耗模型调用。
3. **Given** 一条没有文件线索、意图模糊的请求,**When** 规则无法定性,**Then** 系统调用兜底模型补齐任务类型与工作相关判断,并标记该结论来自模型。

---

### User Story 3 - 分析成本受控且不阻塞 (Priority: P2)

系统在分析时优先用本地规则定字段,只有规则拿不准的请求才调用外部 Haiku,且发送给 Haiku 的是压缩后的信号(几百 token)而非原始请求(常上万至十万 token)。agent 循环续跑轮不触发模型调用。兜底模型调用失败时,保留规则已定结论、标记待重试,不阻塞整批分析。

**Why this priority**: 决定这套分析能否长期低成本运行。功能正确但成本失控会导致无法上线,但它是对 P1 的优化而非前提。

**Independent Test**: 灌入一批混合请求(部分命中内部仓库+明确后缀,部分意图模糊),运行分析,统计模型调用次数远小于物理请求数,且命中规则的请求零模型调用。

**Acceptance Scenarios**:

1. **Given** 一批请求中命中内部仓库且后缀明确的部分,**When** 分析运行,**Then** 这些请求完全由规则定性,不产生任何模型调用。
2. **Given** 兜底模型某次调用超时或报错,**When** 分析继续,**Then** 该请求保留规则结论、被标记为待重试,批处理不中断。
3. **Given** 一个会话内大量 agent 循环续跑轮,**When** 分析运行,**Then** 模型调用次数按逻辑任务数计,显著低于物理请求数。

---

### Edge Cases

- 请求体无法解析为预期的 messages 结构(截断、非 JSON、异常格式)时,系统应跳过分析、标记为不可分析,不影响其余请求。
- 中间数据(待分析队列)在分析成功回写后被删除;若回写成功但删除失败,不得导致同一请求被重复计入聚合。
- 同一会话跨越统计窗口边界时,聚合按窗口切分,续跑轮的分类继承其所属窗口内最近的用户发起轮。
- 待分析数据积压(分析长时间未运行)时,中间数据持续增长,系统需能在一次运行中分批处理并推进水位线。
- 兜底模型返回非预期内容(非 JSON、字段缺失)时,按解析失败处理:保留规则结论并标记待重试。
- 非工作时段判定依赖时间戳时区;跨时区用户的"非工作时段"定义需明确基于网关本地时区。

## Requirements *(mandatory)*

### Functional Requirements

**采集与入库(请求链路,旁路)**

- **FR-001**: 系统 MUST 在转发每条请求的同时,把该请求的原始信息写入 append-only 请求日志,且此写入 MUST NOT 给转发链路增加可感知延迟。
- **FR-002**: 系统 MUST 在入库前从请求日志中提取"压缩信号"(用户意图、涉及文件名、命中的内部仓库、执行的命令动词、用到的工具),并将压缩信号连同其对应用量日志记录的 ID 与用户 ID 存入待分析中间存储。
- **FR-003**: 请求日志与中间存储 MUST NOT 保存明文 Authorization 凭证;身份 MUST 以已解析的用户身份(用户 ID)为准。
- **FR-004**: 压缩信号提取 MUST 丢弃 system prompt、工具 schema 定义、历史助手回复、文件正文全文等无助于画像的内容。

**分析(离线,`check --analyze`)**

- **FR-005**: 系统 MUST 提供 `check --analyze` 命令,异步、离线地处理待分析中间存储中的记录,完全独立于请求转发链路。
- **FR-006**: 对每条待分析记录,系统 MUST 先判定请求角色(用户发起 / 工具续跑 / 子代理);仅用户发起轮计为一件独立逻辑任务,子代理轮与工具续跑轮同等对待(不单独计为逻辑任务、不单独触发模型调用)。
- **FR-007**: 系统 MUST 先用本地规则分类:按文件后缀映射代码方向、按命中内部仓库判定工作相关;规则能定的字段不得再调用模型。
- **FR-008**: 仅当规则无法确定必需字段(任务类型、工作相关、或代码类但方向不定)时,系统 MUST 调用兜底模型,并将规则已定字段作为提示一并发送,要求模型只补空缺、不覆盖已定字段。
- **FR-009**: 工具续跑轮与子代理轮 MUST NOT 触发模型调用;其分类在聚合时继承所属窗口内最近的用户发起轮。
- **FR-010**: 兜底模型调用失败或返回不可解析结果时,系统 MUST 保留规则已定结论、把该记录标记为待重试,并继续处理其余记录(不中断批处理)。
- **FR-011**: 发送给兜底模型的内容 MUST 仅为压缩信号加提示,不得包含原始 messages。

**回写与清理**

- **FR-012**: 分析完成后,系统 MUST 把 任务类型(task_type)、是否工作相关(work_related)、代码方向(code_direction) 回写到该请求对应的用量日志记录。
- **FR-013**: 系统 MUST 把 工作原因(work_reason)与文档动作(doc_activity) 存入用量日志记录的错误信息字段(error_reason),以复用现有字段、避免为低频文本新增列。
- **FR-014**: 某条记录成功回写后,系统 MUST 从待分析中间存储中删除对应记录,避免重复分析与聚合。
- **FR-015**: 系统 MUST 维护增量水位线,使重复运行 `check --analyze` 只处理尚未分析的新记录。
- **FR-015a**: 一条请求分析完成回写后,系统 MUST 删除该请求的**完整原始内容**(请求日志与中间存储中的原始 messages / 请求正文);库中长期只保留压缩信号与分析结论,系统 MUST NOT 为后续扩展而长期留存原始正文。后续如需敏感外流检测,作为独立功能另行设计,不以长期留存原始内容为前提。

**分类字段定义**

- **FR-016**: 每个逻辑任务 MUST 产出:tool_used(工具列表)、task_type(代码/文档/其他)、work_related(布尔)、work_reason(一句话原因)、code_direction(仅代码:前端/后端/固件/运维/移动端/数据/脚本/测试/其他)、doc_activity(仅文档:≤16 字概括)。
- **FR-017**: task_type MUST 以 other 作为兜底,避免把纯问答/闲聊硬塞进代码或文档类。
- **FR-018**: work_related 判定 MUST 将个人副业、学习刷教程、娱乐、求职、私人事务判为非工作相关。

**聚合与评分**

- **FR-019**: 系统 MUST 按人(用户身份)在统计窗口内聚合出:物理请求数、逻辑任务数、任务类型分布、代码方向分布、工具使用分布、工作/非工作任务数、非工作时段任务数、非工作原因抽样。
- **FR-020**: 系统 MUST 依据非工作占比(主因)、非工作时段占比、量级异常计算一个 0~1 的滥用评分。
- **FR-021**: 滥用评分超过阈值的人 MUST 进入人工复核队列,并附非工作原因抽样;系统 MUST NOT 执行任何自动处罚。
- **FR-022**: 评分权重、量级基线、复核阈值、非工作时段定义 MUST 可配置,以便按实际数据校准。

**可观测与报表**

- **FR-023**: 管理员 MUST 能查看按人聚合的画像报表与当前复核队列。
- **FR-024**: 逐条用量日志明细 MUST 能展示回写后的任务类型、代码方向、工作相关标记与原因文本。

### Key Entities *(include if data involved)*

- **请求日志(append-only)**:每条经网关请求的原始记录来源,凭证已剥离/哈希;是压缩信号的提取源。
- **压缩信号**:从一条请求提取的低体量画像输入(意图、文件、仓库、命令、工具),是发给兜底模型的唯一内容。
- **待分析中间记录**:压缩信号 + 对应用量日志 ID + 用户 ID + 时间戳 + 待重试标记;分析成功回写后被删除。
- **分析结论**:一条请求的分类结果(角色、工具、任务类型、工作相关、原因、代码方向、文档动作、是否来自模型)。
- **用量日志记录(usage_logs)**:既有实体,新增承载 task_type / work_related / code_direction,并复用 error_reason 承载 work_reason 与 doc_activity。
- **按人聚合(Rollup)**:某用户某窗口的画像与滥用评分。
- **复核队列条目**:超阈值用户 + 评分 + 原因抽样,供人工判读。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 分析全程为旁路离线执行,请求转发链路的 P99 延迟相比未启用本功能时**无可测量增加**。
- **SC-002**: 对命中内部仓库且文件后缀明确的请求,**100%** 由本地规则定性,产生**零**次模型调用。
- **SC-003**: 在含大量 agent 循环续跑的真实流量上,模型调用次数相比物理请求数下降**至少 5 倍**。
- **SC-004**: 发送给兜底模型的单请求输入体量相比原始请求压缩**两个数量级**(典型从 1w~10w+ token 降到 150~400 token)。
- **SC-005**: 分析完成后,待分析中间存储中对应记录被清理,**不残留**已成功回写的数据;重复运行不产生重复聚合。
- **SC-006**: 兜底模型出现调用失败时,当批分析仍能跑完其余记录、**0** 次因单条失败而整批中断,失败记录被标记待重试。
- **SC-007**: 管理员能在报表中对每个活跃用户看到逻辑任务数、工作占比与滥用评分,并对超阈值用户看到原因抽样。

## Assumptions

- 身份归属以现有 usage_logs 的用户 ID 为准:本网关的 API key 已绑定到具体用户,故"到人"聚合成立,原始需求中"每人是否独立 key"的待确认项在本项目已解决;IP 仅作异常交叉验证的兜底信号。
- 分析对象为经网关的 Claude Code(Anthropic messages 风格)流量;跑批频率(小时级/天级)可配置,由运维按需触发或定时执行。
- 不做 PII 脱敏,只做压缩;压缩后信号本就低 PII。完整原始内容仅短暂驻留于请求日志/中间存储,分析回写后即删除全部原始内容(见 FR-015a),库中长期只保留压缩信号与分析结论。这是隐私面最小的选择;未来的敏感外流检测将作为独立功能,不依赖长期留存原始正文。
- 非工作时段与量级基线采用可配置默认值(如 22:00–08:00 及周末为非工作时段、单窗口逻辑任务基线 60、阈值 0.5),上线后按真实数据校准。
- 复用 usage_logs 现有 error_reason 字段承载 work_reason 与 doc_activity,避免为低频文本字段新增列;新增 task_type / work_related / code_direction 三列。
- 本功能只做识别与提示,不做自动封禁或限流等处罚。
- 子代理(subagent)发起的请求归为"工具续跑",不计为独立逻辑任务、不单独触发模型调用。
